# Feature Specification: 단계 분리형 AI 블로그 생성 재정의

**Feature Branch**: `생성하지 않음 (사용자 요청: md만 생성)`  
**Created**: 2026-03-23  
**Status**: Draft  
**Input**: User description: "현재 AI 모델에 대한 정의를 다시 할거야. generate.ts 위주로 다시 하고, 기본적인 모델은 gpt-4o-mini로 간다. DB에 저장된 데이터를 바로 읽어 학습하지 않고 요약을 남긴 뒤 이를 참고한다. 들어온 이미지를 분석한 뒤 상위 RAG를 참고해 새로운 글을 생성한다. 각 단계는 별도 API 호출이어야 하며, 오류가 발생하면 해당 단계에서 즉시 반환한다."

## Background & Rationale

- 현재 생성 흐름은 업로드 이미지 분석 이후 바로 임베딩 검색과 최종 글 생성으로 이어지며, 단계별 품질 통제 지점이 충분히 분리되어 있지 않다.
- 현재 게시글 저장 구조에는 재사용 가능한 `summary` 개념이 없어, 과거 글의 본문이 그대로 참조 데이터로 사용된다.
- 사용자는 기존 bad case 코드의 "단계 구분"만 참고하고, 실제 동작은 요약 기반 메모리와 상위 RAG를 중심으로 다시 정의하기를 원한다.
- 이번 재정의의 목적은 더 나은 글 품질, 단계별 실패 원인 분리, 과거 글 재사용 방식의 정제에 있다.

## Constraints & Decisions

- 이번 재정의의 기본 생성 모델은 `gpt-4o-mini`로 고정한다.
- 생성 파이프라인은 한 번의 호출로 끝나는 방식이 아니라, 순차적인 독립 단계 호출로 구성한다.
- 공개 생성 API는 단일 이미지용 `createBlogFromImage`와 다중 이미지 리뷰용 `createBlogReview`를 유지하고, 실제 단계는 `internalAction`/`internalQuery`/`internalMutation` 단위로 분리한다.
- `/generate` 화면은 이미지 1장이면 단일 이미지 글 생성, 2~20장이면 다중 이미지 리뷰 글 생성으로 분기한다.
- 생성 시작 전 이미지 개수, 이미지 URL 존재 여부, `memo`, `keywords`를 정규화하고 검증한다.
- 서버 내부 자동 재시도는 허용하지 않으며, 실패 응답에는 클라이언트 재요청 가능성을 나타내는 `retryable`를 포함한다.
- 과거 게시글은 원문 전체를 직접 주입하는 방식이 아니라, 저장된 요약 정보를 우선 참조한다.
- 게시글의 `summary`는 저장 또는 수정 이후 비동기 작업으로 생성하거나 갱신한다.
- 초기 배포에서는 기존 게시글 `summary`를 자동 일괄 백필하지 않고, 필요 시 수동 backfill mutation으로 채운다.
- 제공된 bad case 코드는 "단계별 처리 흐름이 필요하다"는 참고 근거로만 사용하고, 프롬프트/구조/폴백 전략을 그대로 답습하지 않는다.

## Clarifications

### Session 2026-03-23

- Q: 새 글 생성 요청 시 참고 후보 과거 글에 `summary`가 없으면 어떻게 처리하는가? → A: 요약이 없는 후보는 현재 요청에서 제외하고, 남은 요약만으로 계속 진행한다.
- Q: 다중 이미지 요청에서 일부 이미지만 분석에 실패하면 어떻게 처리하는가? → A: 이미지 하나라도 분석에 실패하면 전체 요청을 이미지 분석 단계 실패로 처리한다.
- Q: 특정 단계의 AI 응답이 JSON 또는 기대 형식을 만족하지 못하면 어떻게 처리하는가? → A: 서버 내부 자동 재시도 없이 해당 단계를 즉시 실패 처리하고, 실패 응답에 `retryable`를 포함한다.
- Q: 상위 RAG가 관련 게시글을 찾지 못하거나 품질 기준에 못 미치는 참고만 찾으면 어떻게 처리하는가? → A: 상위 RAG 단계를 실패 처리하고 요청 전체를 중단한다.
- Q: 동일 요청이 직전 실패 직후 다시 들어오면 중간 산출물을 재사용하는가? → A: 실패한 요청의 중간 산출물은 재사용하지 않고 항상 첫 단계부터 다시 실행한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이미지 기반 새 글 생성 품질 개선 (Priority: P1)

사용자는 이미지를 업로드했을 때, 이미지 자체의 관찰 결과와 자신의 과거 글 요약을 함께 반영한 새 글 초안을 받고 싶다.

**Why this priority**: 이 기능의 핵심 가치는 업로드한 입력과 사용자 고유 문맥을 함께 반영한 글 생성 품질에 있다.

**Independent Test**: `/generate` 화면에서 이미지 1장 요청과 2장 이상 요청을 각각 실행했을 때, 시스템이 이미지 분석과 요약 기반 참고 맥락을 거친 결과를 올바른 생성 타입으로 반환하면 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자의 과거 게시글 요약이 존재하고 새 이미지가 입력된 상태에서, **When** 사용자가 새 글 생성을 요청하면, **Then** 시스템은 이미지 분석 결과와 관련 요약 맥락을 반영한 새 글을 반환해야 한다.
2. **Given** 관련도가 높은 과거 요약을 찾지 못했거나 참고 품질이 기준에 못 미치는 상태에서, **When** 사용자가 새 글 생성을 요청하면, **Then** 시스템은 상위 RAG 단계를 실패 처리하고 최종 글 생성 단계로 진행하지 않아야 한다.

---

### User Story 2 - 단계별 실패 지점 확인 (Priority: P1)

사용자는 생성이 실패했을 때 어디에서 실패했는지 알 수 있어야 하며, 앞 단계가 실패한 경우 뒤 단계가 실행되지 않기를 원한다.

**Why this priority**: 현재 요구사항의 핵심 제약은 "각 단계별 API 호출"과 "에러 단계 즉시 반환"이므로, 실패 지점 분리는 구현보다 먼저 보장되어야 한다.

**Independent Test**: 각 단계별로 의도적인 실패 조건을 주었을 때, 시스템이 해당 단계에서 중단되고 이후 단계를 실행하지 않으면 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 이미지 분석 단계 응답이 비어 있거나 유효하지 않은 상태에서, **When** 생성 요청이 실행되면, **Then** 시스템은 이미지 분석 단계 실패를 반환하고 RAG 또는 최종 생성 단계로 진행하지 않아야 한다.
2. **Given** 상위 RAG 단계에서 참고 맥락 구성이 실패한 상태에서, **When** 생성 요청이 실행되면, **Then** 시스템은 RAG 단계 실패를 반환하고 최종 글 생성 단계로 진행하지 않아야 한다.
3. **Given** 다중 이미지 요청에서 이미지 중 하나라도 분석에 실패한 상태에서, **When** 생성 요청이 실행되면, **Then** 시스템은 전체 요청을 이미지 분석 단계 실패로 반환하고 후속 단계로 진행하지 않아야 한다.
4. **Given** 어떤 단계의 AI 응답이 JSON 또는 기대 형식을 만족하지 못한 상태에서, **When** 해당 단계 결과를 검증하면, **Then** 시스템은 서버 내부 자동 재시도 없이 해당 단계를 즉시 실패 처리하고 실패 응답의 `retryable` 값을 함께 반환하며 후속 단계로 진행하지 않아야 한다.
5. **Given** 동일한 생성 요청이 직전 실패 직후 다시 들어온 상태에서, **When** 시스템이 새 요청을 처리하면, **Then** 시스템은 이전 실패 요청의 중간 산출물을 재사용하지 않고 첫 단계부터 다시 실행해야 한다.

### User Story 3 - 요약 기반 과거 글 재사용 (Priority: P2)

반복 사용자는 자신의 과거 글을 직접 복제당하지 않으면서도, 요약된 문맥을 통해 일관된 톤과 주제 연결성을 유지하고 싶다.

**Why this priority**: raw 본문을 그대로 재사용하면 잡음이 많고 품질이 흔들릴 수 있으므로, 요약 기반 재사용은 장기 품질 개선에 직접 연결된다.

**Independent Test**: 과거 글 원문과 요약이 함께 존재할 때, 생성 흐름이 원문 전체 대신 요약 맥락을 우선 사용하면 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 과거 게시글에 재사용 가능한 요약이 저장된 상태에서, **When** 새 글 생성 요청이 실행되면, **Then** 시스템은 원문 전체가 아니라 저장된 요약을 우선 참고 데이터로 사용해야 한다.
2. **Given** 참조 후보 게시글에 요약이 없는 상태에서, **When** 해당 게시글이 참고 후보로 검토되면, **Then** 시스템은 해당 게시글을 현재 요청의 참고 후보에서 제외하고 남은 요약만으로 다음 단계로 진행해야 한다.

---

### Edge Cases

- 기존 게시글에는 `summary`가 없고 새 구조만 이를 요구하는 경우, 해당 게시글은 현재 생성 요청의 참고 후보에서 제외하고 남은 요약만으로 진행한다.
- `/generate`에서 이미지가 0장이거나 21장 이상이면, AI 호출 전에 입력 검증 오류를 반환한다.
- `/generate`에서 이미지가 1장이면 단일 이미지 글 생성으로, 2~20장이면 리뷰 글 생성으로 분기한다.
- 여러 장의 이미지 중 하나라도 분석에 실패하면, 요청 전체를 이미지 분석 단계 실패로 처리하고 후속 단계로 진행하지 않는다.
- 상위 RAG가 관련 게시글을 찾지 못하거나 낮은 품질의 참고만 찾은 경우, 상위 RAG 단계를 실패 처리하고 생성 단계를 진행하지 않는다.
- 특정 단계의 AI 응답이 JSON 또는 기대 형식을 만족하지 못하는 경우, 서버 내부 자동 재시도 없이 해당 단계를 즉시 실패 처리하고 실패 응답에 `retryable`를 포함한다.
- `memo`는 trim 후 빈 문자열이면 무시하고, `keywords`는 trim 후 빈 값을 제거한 뒤 최대 10개까지만 사용한다.
- 동일 요청이 이전 실패 직후 다시 들어온 경우에도, 실패한 요청의 중간 산출물을 재사용하지 않고 항상 첫 단계부터 다시 시작한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 블로그 생성 흐름을 최소한 다음의 순차 단계로 분리해야 한다: 과거 글 요약 준비, 입력 이미지 분석, 상위 RAG 참고 맥락 구성, 최종 글 생성.
- **FR-002**: 시스템은 공개 생성 API 내부에서 각 단계를 서로 독립된 `internalAction`/`internalQuery`/`internalMutation` 호출 단위로 실행해야 하며, 어떤 단계라도 실패하면 해당 단계에서 즉시 종료하고 이후 단계를 실행하면 안 된다.
- **FR-003**: 시스템은 과거 게시글을 생성 맥락으로 사용할 때 저장된 요약 정보를 우선 사용해야 하며, 요약이 존재하는 경우 원문 전체를 직접 참조 입력으로 사용하면 안 된다.
- **FR-004**: 시스템은 향후 재사용을 위해 게시글 단위의 요약 정보를 저장 또는 수정 이후 비동기 작업으로 생성하거나 갱신할 수 있어야 한다.
- **FR-005**: 시스템은 참조 후보 게시글에 요약이 없는 경우, 해당 후보를 현재 생성 요청에서 제외하고 남은 요약만으로 계속 진행해야 한다.
- **FR-006**: 시스템은 들어온 이미지를 최종 글 생성 전에 반드시 분석해야 하며, 분석 결과는 후속 단계에서 재사용 가능한 구조화된 관찰 정보여야 한다.
- **FR-007**: 시스템은 이미지 분석 결과를 기반으로 상위 RAG용 검색 질의 또는 참고 맥락을 구성해야 하며, 준비된 `summary` 후보가 없거나 최종 선택된 참고 요약이 기본 임계값 3개에 미달하면 상위 RAG 단계를 실패 처리해야 한다. 기본 임계값은 테스트 결과에 따라 3개 이상으로 상향 가능해야 한다.
- **FR-008**: 시스템은 상위 RAG 단계에서 사용자 본인의 과거 글 요약만 참조해야 하며, 다른 사용자의 데이터가 검색되거나 섞이면 안 된다.
- **FR-009**: 시스템은 최종 글 생성 시 이미지 분석 결과와 상위 RAG 참고 맥락을 함께 반영하되, 참조 내용을 단순 재서술하지 않고 새 글로 재구성해야 한다.
- **FR-010**: 시스템은 이번 재정의에서 이미지 분석, 요약 생성, 상위 RAG 맥락 구성, 최종 글 생성에 사용하는 기본 생성 모델을 `gpt-4o-mini`로 사용해야 한다.
- **FR-011**: 시스템은 `/generate` 화면에서 단일 이미지 글 생성과 다중 이미지 리뷰 글 생성을 모두 지원해야 하며, 이미지가 1장이면 단일 생성, 2~20장이면 리뷰 생성으로 분기해야 한다. 다중 이미지 요청에서는 이미지 하나라도 분석에 실패하면 전체 요청을 이미지 분석 단계 실패로 처리해야 한다.
- **FR-012**: 시스템은 실패 응답에 최소한 `failedStage`, `code`, 사용자에게 보여줄 수 있는 명확한 실패 사유 `message`, 재요청 가능성 판별용 `retryable`를 포함해야 한다.
- **FR-013**: 시스템은 이전 단계의 결과가 비어 있거나 형식 검증을 통과하지 못하면, 이를 정상 결과로 간주하고 다음 단계로 넘기면 안 되며 서버 내부 자동 재시도 없이 해당 단계를 즉시 실패 처리해야 한다.
- **FR-014**: 시스템은 동일한 생성 요청이 이전 실패 직후 다시 들어오더라도, 실패한 요청의 중간 산출물을 재사용하지 않고 첫 단계부터 다시 실행해야 한다.
- **FR-015**: 시스템은 어떤 AI 호출도 시작하기 전에 입력을 검증해야 하며, 단일 생성은 이미지 1장만 허용하고 리뷰 생성은 이미지 2~20장만 허용해야 한다. 모든 이미지 URL은 비어 있으면 안 되며, `memo`는 trim 후 빈 값이면 제거하고, `keywords`는 trim 후 빈 값을 제거한 뒤 최대 10개까지만 허용해야 한다.
- **FR-016**: 시스템은 초기 배포에서 기존 게시글 `summary`에 대해 자동 일괄 백필을 수행하지 않아야 하며, 필요 시 수동 backfill mutation으로만 재생성해야 한다.

### Key Entities *(include if feature involves data)*

- **Post Summary**: 과거 게시글을 원문 대신 재사용하기 위한 축약 표현으로, 이후 RAG와 스타일 참고의 기본 단위가 된다.
- **Summary Generation Job**: 게시글 저장 또는 수정 이후 실행되어 `summary`를 생성하거나 갱신하는 비동기 작업이다.
- **Image Analysis Result**: 업로드된 이미지에서 관찰된 요소를 정리한 단계 결과로, 후속 검색과 글 생성의 입력이 된다.
- **RAG Context Bundle**: 이미지 분석 결과와 요약 저장소를 기반으로 구성된 상위 참고 맥락이다.
- **Generation Stage Result**: 각 단계의 성공/실패 상태, 출력, 실패 사유를 나타내는 실행 단위 결과이다.
- **Generated Draft**: 이미지 분석과 RAG 맥락을 종합해 생성된 최종 블로그 초안이다.

## Constitution Alignment *(mandatory)*

- **CA-001 인증/권한**: 요약 조회, RAG 검색, 최종 저장은 모두 현재 인증된 사용자 범위 안에서만 이루어져야 한다.
- **CA-002 입력 검증**: 이미지 입력과 생성 요청 파라미터는 각 단계 실행 전에 검증되어야 하며, 유효하지 않은 입력은 조기에 차단되어야 한다.
- **CA-003 AI 출력 계약**: 각 단계는 기대한 형식의 산출물 또는 명시적인 실패를 반환해야 하며, 비어 있는 응답을 성공으로 취급하면 안 된다.
- **CA-004 데이터 일관성**: `summary` 도입 시 저장 구조, 조회 흐름, 검색 기준이 함께 맞물려 수정되어야 한다.
- **CA-005 수정 범위**: 중심 변경 지점은 `generate.ts`이지만, 해당 요구사항을 충족하기 위해 필요한 스키마와 헬퍼 계층 변경은 함께 허용된다.

## Assumptions

- 본 명세에서 "학습"은 파인튜닝이 아니라 생성 시점의 참고 맥락 주입을 의미한다.
- "상위 RAG"는 이미지 분석 결과를 그대로 검색에 쓰는 수준을 넘어서, 검색용 요약/질의/참고 묶음을 먼저 만들고 이를 기준으로 관련 요약을 참조하는 흐름으로 해석한다.
- `/generate`는 하나의 화면에서 단일 이미지 글 생성과 다중 이미지 리뷰 글 생성을 모두 처리한다.
- 기존 게시글에 `summary`가 없는 경우, 해당 게시글은 현재 생성 요청의 참고 후보에서 제외되며 초기 구현에서는 수동 backfill mutation으로만 채운다.
- 게시글의 `summary` 생성·갱신은 새 글 생성 요청 경로 안에서 동기 처리하지 않고, 게시글 저장 또는 수정 이후 별도 비동기 작업으로 처리한다.
- bad case 예시는 현재 요구사항의 방향을 설명하는 반례로만 사용하며, 성공 기준으로 채택하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 성공 또는 실패 여부와 관계없이, 요청의 95% 이상은 "어느 단계에서 끝났는지"를 식별 가능한 결과를 한 번의 실행 내에 반환한다.
- **SC-002**: 상위 RAG가 성공한 요청의 90% 이상에서, 생성 결과는 이미지 기반 정보와 과거 요약 기반 맥락을 모두 반영한 것으로 검토된다.
- **SC-003**: 특정 단계가 실패한 사례의 100%에서 이후 단계는 실행되지 않는다.
- **SC-004**: 재설계 후 동일 주제의 생성 결과 10건을 블라인드 비교했을 때, 작성자 또는 운영자가 "기존 방식보다 더 자연스럽고 관련성이 높다"고 판단한 비율이 70% 이상이어야 한다.
