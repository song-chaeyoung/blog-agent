# Phase 0 Research: 단계 분리형 AI 블로그 생성 재정의

## 결정 1. `summary`는 게시글 저장/수정 이후 비동기 작업으로 생성·갱신한다

- **Decision**: [`convex/posts.ts`](/C:/Users/adcapsule/Desktop/ts-study/blog-agent/convex/posts.ts)의 `createPost`, `bulkCreatePosts`, `updatePost`는 게시글 저장 직후 `ctx.scheduler.runAfter`로 `summary` 생성 작업을 예약한다.
- **Rationale**: 사용자 저장 경로에 요약 생성과 임베딩 생성을 동기적으로 넣으면 지연이 커지고 실패 지점이 저장 실패와 섞인다. 명세는 `summary`를 재사용 자산으로 요구하지만 생성 요청 경로를 가볍게 유지하길 원하므로, 비동기 후처리가 가장 일관된다.
- **Alternatives considered**:
  - 저장 요청 안에서 동기 생성: 실패 원인이 저장 실패와 AI 실패로 혼합되어 사용자 경험이 악화된다.
  - 생성 요청 시 지연 생성: 현재 요청에서 `summary` 없는 글을 제외한다는 명세와 충돌한다.
  - 이번 범위에서 생성 생략: 장기적으로 RAG 품질이 누적되지 않는다.

## 결정 2. RAG는 원문 `content`가 아니라 `summary`와 `embedding`(summary 기반 벡터)을 사용한다

- **Decision**: `posts`에 `summary`를 추가하고, 기존 `embedding` 필드의 의미를 `summary` 기반 벡터로 재정의하여 상위 RAG는 이 조합만 사용한다.
- **Rationale**: 명세의 핵심은 "DB 원문을 바로 읽어 학습하지 않고 요약을 남긴 뒤 이를 참고한다"는 점이다. 원문 임베딩을 유지한 채 `summary`만 프롬프트에 넣으면 검색 기준은 여전히 원문에 묶여 요구사항을 반만 만족하게 된다.
- **Alternatives considered**:
  - 기존 `embedding` 필드를 그대로 유지: 검색 단계에서 원문 기반 편향이 남는다.
  - `summary`만 저장하고 벡터는 원문 유지: 검색과 참조 기준이 어긋나 추론 가능성이 떨어진다.

## 결정 3. 생성 파이프라인은 공개 action 1개 + 내부 스테이지 함수 여러 개로 분리한다

- **Decision**: 프런트엔드가 호출하는 공개 action은 유지하되, 내부에서는 `prepareSummaryCandidates`, `analyzeImages`, `buildRagContext`, `composeDraft` 같은 internal 함수 호출로 스테이지를 나눈다.
- **Rationale**: 프런트에서 여러 액션을 직접 호출하게 하면 인증, 실패 처리, 중간 상태 관리가 UI로 새어 나온다. 반대로 내부 스테이지 함수 분리는 "각 단계별 API 호출"이라는 요구를 유지하면서도 오케스트레이션 책임을 서버 쪽에 묶어 둔다.
- **Alternatives considered**:
  - 단일 action 내부에 로직 계속 유지: 실패 지점 분리와 테스트 독립성이 약하다.
  - 프런트에서 스테이지별 action 직접 호출: 중간 산출물 재사용 금지, 인증, 예외 처리 정책이 UI에 흩어진다.

## 결정 4. 실패 응답은 예외 문자열이 아니라 판별 가능한 계약으로 통일한다

- **Decision**: 생성 결과 타입을 `success | failure` 유니온으로 정의하고, 실패 시 `failedStage`, `code`, `message`, `retryable`을 포함한다.
- **Rationale**: 현재 UI는 예외를 toast 문자열로만 처리한다. 명세는 "실패한 단계"와 "명확한 실패 사유"를 요구하므로, 반환형 자체가 이를 표현해야 한다. 또한 서버 내부 자동 재시도를 금지하고 클라이언트 재요청 가능성만 `retryable`로 전달해야 운영 규칙이 단순해진다.
- **Alternatives considered**:
  - 예외 메시지 파싱: 안정적이지 않고 다국어/문구 수정에 취약하다.
  - 실패 시 `null` 반환: 어떤 단계에서 실패했는지 알 수 없다.

## 결정 5. 생성 체인은 `gpt-4o-mini`로 통일한다

- **Decision**: 이미지 분석, 요약 생성, 검색 질의/참고 맥락 구성, 최종 블로그 초안 생성 모두 `gpt-4o-mini`를 사용한다. 임베딩은 `text-embedding-3-small`을 유지한다.
- **Rationale**: 프로젝트 헌법은 AI 호출 모델을 `gpt-4o-mini`로 고정한다. 구현 단계에서 별도 예외를 만들기보다, 전체 생성 체인을 같은 모델 기준으로 맞추는 편이 헌법 준수와 운영 단순성 측면에서 낫다.
- **Alternatives considered**:
  - 최종 글 생성만 `gpt-4o` 사용: 헌법과 충돌한다.
  - 단계별로 모델 혼합 사용: 운영 규칙과 디버깅 포인트가 늘어난다.

## 결정 6. 다중 이미지 흐름은 부분 성공을 허용하지 않는다

- **Decision**: 다중 이미지 리뷰 글에서 이미지 하나라도 분석 실패하면 전체 요청을 `image-analysis` 단계 실패로 반환한다.
- **Rationale**: 이 결정은 이미 명세에 들어가 있으며, 현재 구현처럼 일부 성공 이미지로 계속 진행하면 사용자 입력과 결과 사이의 대응이 깨진다. 리뷰 글은 이미지 집합 전체의 서사를 다루므로 부분 성공보다 명시적 실패가 더 안전하다.
- **Alternatives considered**:
  - 성공한 이미지만으로 계속 생성: 사용자가 기대한 이미지 집합 전체를 반영하지 못한다.
  - 실패 이미지만 빈 캡션 처리: 실패를 숨겨 디버깅과 신뢰성을 떨어뜨린다.

## 결정 7. 사용자 격리 검사는 모든 스테이지에서 중복 확인한다

- **Decision**: 공개 action 시작 시 인증을 확인하고, 요약 후보 조회 및 벡터 검색 시에도 `userId` 필터를 다시 적용한다.
- **Rationale**: 헌법은 사용자 데이터 격리를 최우선 원칙으로 둔다. 생성 파이프라인이 길어질수록 초기 인증만 믿는 것보다, 데이터 조회 시점마다 경계를 재확인하는 편이 안전하다.
- **Alternatives considered**:
  - 최초 인증 후 모든 내부 단계에서 사용자 정보 재검증 생략: 유지보수 중 필터 누락 위험이 커진다.

## 결정 8. 상위 RAG의 최종 참조는 기본 3개 이상을 요구한다

- **Decision**: `rag-context` 단계는 최종 참조 요약이 기본 임계값 3개 이상일 때만 성공으로 간주한다. 임계값은 테스트 결과에 따라 3개 이상으로 상향 가능하다.
- **Rationale**: 단일 참조 기준은 문맥 편향과 품질 분산이 커서 생성 품질 안정성이 낮다. 최소 3개는 다양성과 일관성의 균형을 맞추는 현실적인 하한이다.
- **Alternatives considered**:
  - 최종 참조 1개 이상: 근거 다양성이 부족해 품질 편차가 커진다.
  - 고정 5개 이상: 초기 데이터가 적은 사용자에서 실패율이 과도하게 상승할 수 있다.

## 결과 요약

- `summary` 중심 데이터 모델과 비동기 요약 생성 작업을 도입한다.
- `convex/generate.ts`는 단계 오케스트레이터가 되고, 실제 단계는 내부 함수로 쪼갠다.
- 생성 응답은 성공/실패 유니온으로 고정해 프런트가 단계 실패를 정확히 표시할 수 있게 한다.
- 모든 생성 단계는 `gpt-4o-mini`, 검색 벡터는 `text-embedding-3-small`로 통일한다.
